# SP970 开发工具梳理（Agent 工程视角）

> 本文档说明本项目开发/验证/发布流程的**工具设计原则**（第一性原理分析），供维护者与开发 Agent 参考。工具脚本位于维护者工作区 `experiments/scripts/`（本地私有，不入仓），职责见下文矩阵。

## 1. 工具的本质（第一性原理）

**工具 = 把"重复出现 + 精确执行 + 高代价 + 知识密集 + 跨会话一致"的操作固化为确定性程序。**

需要工具（而非每次临场）的原因：
- **认知负担**：每次重拼命令、记参数
- **出错风险**：顺序/保护/坑（如刷 partition 毁 NV/IMEI）
- **漂移**：跨会话做法不一致
- **知识丢失**：代理、路径、API、坑只存在于一次会话

## 2. 判断标准：工具化 vs 临场（5 问）

| 问 | 是 → 倾向 |
|---|---|
| 1. 重复频率高？（每次会话都碰）| 工具 |
| 2. 有唯一正确做法？（无歧义）| 工具 |
| 3. 出错代价高？（刷机/NV/删除/Release）| 工具 |
| 4. 知识密度高？（API/代理/路径/坑）| 工具 |
| 5. 跨会话一致必需？| 工具 |

**≥4 问 YES → 工具化；≤2 → 临场；3 → 权衡。**

## 3. 需求盘点 + 决策矩阵

### L1 设备运维

| 需求 | 操作 | 决策 | 依据 |
|---|---|---|---|
| 执行设备命令 | SSH 任意命令 | **工具** `dev_ssh.py` | 高频 + paramiko 封装 |
| 部署文件到设备 | 本地→设备 | **工具** `dev_deploy.py` | busybox 无 sftp-server 的坑 |
| 设备状态检查 | 9 项验证 | **工具** `verify_build.py` | 固定检查 + 跨会话一致 |
| 刷机 | fastboot 8 镜像 | **工具** `flash.py` | 高风险 + NV 保护（写死不刷 partition）|
| 设备状态查询/恢复 | `sp970-link card/status/up`（设备端）+ alpine-tools 薄包装 | **工具** | 状态机 + power-cycle 知识在设备端，主机端只透传 |
| NV 恢复 | 救命操作 | **工具** `restore_nv.py` | 高代价 + 知识密集 |

### L2 CI/CD

| 需求 | 操作 | 决策 | 依据 |
|---|---|---|---|
| 产物下载 | CI artifact | **工具** `download_build.py` | 代理 + API 知识 |
| CI 状态 | runs 查询 | **工具** `check_runs.py` | 高频 |
| 失败定位 | job/日志 | **工具** `check_jobs.py`（含日志下载）| 固定排查流程 |
| Release 检查 | assets | **工具** `check_release.py` | API 知识 |

### L3 GitHub 流程

| 需求 | 操作 | 决策 | 依据 |
|---|---|---|---|
| PR 创建 + 分支保护 | API | **工具** `pr_main.py` | 流程封装（保护规则是坑）|
| PR 合并 | API | **工具** `merge_pr.py` | 流程封装（build 门禁）|

### L4 临场（不该工具化）

| 需求 | 操作 | 决策 | 依据 |
|---|---|---|---|
| 创建仓库 | API | **临场**（一次性）| 频率极低 |
| 删除 Release/tag | API | **临场**（一次性）| 频率极低 |
| 打 tag | `git tag` | **临场** | 简单 |
| 文本分析 | grep/awk | **临场** | 灵活 |
| 实验研究 | 任意 | **临场** | 探索性，无固定答案 |
| **发布决策**（实机测试通过/可发布）| 判断 | **临场**（Agent 决策）| 决策性，不可自动化 |

## 4. 工具需求规范（工具应该长什么样）

1. **单职责**——一个工具一件事（`dev_ssh` 不混 `verify`）
2. **输出可解析**——固定格式/JSON/稳定退出码（Agent 能自动消费）
3. **参数明确**——`--help` 或 README 用法
4. **失败可诊断**——错误含上下文（不吞异常）
5. **可组合**——输出能喂下一个工具（`flash` 后接 `verify`）
6. **副作用保护**——刷机/删除类带确认或写死保护（如 `flash.py` 不刷 partition）
7. **文档化**——工具索引在 `experiments/scripts/README.md`（维护者工作区）
8. **状态语义正确**——输出能表达"未知/查询失败"与"确认值"的区别（教训：sp970-link v1 把 QMI 查询失败谎报成"卡缺席 absent"，误导恢复动作；v2 引入 `unknown` 态区分。工具的输出语义错误会直接导致消费者做出错误决策）

### 设备端工具（固件内置 `/usr/local/bin/`）

`sp970-link` 是"单一事实源 + 恢复原语"的典范：把 6 个分散状态源（QMI UIM/NAS、MM D-Bus、内核 netdev、sysfs bam-dmux、路由表、外网）收敛成一维状态机（card 4 态 / link 6 态），把知识密集的恢复序列（停 MM→power-cycle→provision→注册→起 MM）固化为幂等 `up`。主机端 alpine-tools 只做薄包装，状态机唯一实现在设备端。设计演进与状态语义见维护者本地 `docs/SP970-sp970-link状态机.md`（不入公开仓）。

## 5. 现有工具集评估

| 状态 | 工具 | 说明 |
|---|---|---|
| ✅ 合理 | dev_ssh / dev_deploy / verify / flash / download / check_runs / check_jobs / check_release / pr_main / merge_pr | 符合 5 问标准 |
| 🔧 可合并 | check_jobs + 日志下载 | 同一排查流程 |
| 🔧 低频 | create_repo / delete_release | 保留但标注低频 |
| ❌ 缺失 | **半自动发布脚本** | 发布流程 = PR→merge→tag 机械部分可脚本化，但**实机测试是人工决策点**，应卡在中间 |

## 6. 关键结论

1. **工具化的边界** = 5 问的 YES 数。当前工具集基本正确，错在"该临场的工具化"（create_repo/delete_release 低频）和"该固化的没固化"（发布机械步骤）
2. **最高价值工具** = dev_ssh / verify / flash（设备侧，反复用 + 高代价）
3. **最不该工具化** = 发布决策、实验研究（Agent 判断力所在，工具化反而僵化）
4. **工具需求核心** = 输出可解析 + 副作用保护 + 单职责——决定 Agent 能否可靠消费工具结果
